01 / Service Opportunity

选择的服务：足球技术动作反馈

在足球训练中，专业反馈依赖教练观察、动作示范和反复纠错。我的八年以上训练经历使我熟悉这种服务过程；Kick AI 尝试以单机位视频连接动作阶段与反馈报告。

对象想完成的任务待验证的困难
训练者 / 家长上传一次练习，明确最先要改的动作难以方便获得及时、可复看的结构化反馈
足球教练 / 创作者标准化高频反馈并持续提供服务重复解释相似问题，服务规模受时间限制

02为什么适合探索 Agent 化

  • 可标准化：目标、常见问题、练习建议及复测方式可以沉淀为服务模板。
  • 必须个性化：建议要考虑用户目标、训练频率、当前动作和场地条件。
  • 需要人工兜底：动作识别不足或涉及伤痛时，模型不应给出确定性判断。

03核心取舍：先辅助，再自动化

先做「教练可审阅的反馈草稿」，再讨论「自动交付的 Agent」。
视频识别质量是上游约束。再流畅的文案也不能弥补错误的动作判断。

首版闭环设为：教练输入经验 → AI 按模板辅助生成 → 教练纠正 → 用户复测。暂不承诺完全自动诊断或动作评分准确率。

02 / Creator-in-the-loop

一个可检验的创作者 Agent MVP

先验证服务质量，再提高自动化程度。

阶段创作者（教练）服务用户（训练者）
1 · 配置录入服务范围、问题模板与安全边界选择技术动作及训练目标
2 · 收集提供可复核的示例与验收标准上传单段视频或训练记录并授权使用
3 · 生成核对动作证据、定位与练习建议看到分阶段反馈和最优先的 1–2 项问题
4 · 复核低置信度或风险建议由人工确认重录、补充输入或请求人工反馈
5 · 复测依据高频错误修订知识卡与模板再次提交相同动作，对照训练目标

05服务输出的验收结构

  • 输入：练习类型、目标、单段视频 / 动作记录、场地器材。
  • 证据：对应视频片段、动作阶段及观察依据；缺失证据时明确「无法判断」。
  • 建议：只给优先的 1–2 项，附原因、操作方式与复测标准。
  • 边界：疑似伤害、危险动作、未成年人隐私或识别失败，应停止自动判断并转人工。

06规则与模型的责任分工

规则 / 人工决定模型辅助处理
上传限制、隐私同意、任务状态、风险词拦截把教练经验整理为结构化知识卡
检测不足时重新上传 / 转人工依核验的观察结果生成通俗反馈
教练修订、确认发布与版本控制按用户目标改写练习说明及跟进话术

判断依据：模型适合解释和表达，动作判断需要可追溯证据；服务边界、隐私、风险处置不应完全交给自由生成。

03 / Platform Capabilities

从服务闭环反推平台能力

能力要解决的创作者问题优先级
知识 / 服务模板难将经验转换为 Agent 可执行步骤P0
调试与坏例库回答看似合理但不符合专业标准P0
人工审核 / 版本管理纠正后如何稳定更新后续服务P0
任务记录与复测如何确认用户确实完成后续任务P1
服务页与分发如何展示边界、建立信任并引导试用P1
04 / Validation Plan

先小规模试错，再判断扩展条件

计划（未执行）：招募 2–3 名有真实指导经验的教练和 5–10 名训练者，统一任务脚本测试首版服务。这是拟议样本，不代表已有测试结果。

  • 创作者可用性：首版服务配置完成率、配置耗时、反复修改节点。
  • 反馈质量：由教练逐项判断「证据可追溯 / 问题成立 / 建议可执行」的通过比例。
  • 用户任务：有效任务完成率、重录率、转人工率、复测率。
  • 风险成本：单次处理耗时、模型调用成本、不安全建议比例；严重安全错误立即回退人工。

09数据会如何改变决策

若教练反复改写同类建议，优先修订知识结构和模板；若错误来自视频识别，优先补充证据或缩窄动作范围；若用户不愿复测，检查反馈是否足够具体、任务是否过重。

希望验证的核心假设：帮助专业人士以较低成本把经验组织成「可测试、可纠错、可交付」的 Agent 服务，可能比增加预置功能更有价值。具体成效需要创作者与用户共同验证。
