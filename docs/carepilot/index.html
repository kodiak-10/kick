几个名字很像，但做的事不同

容易混淆口语解释对我们有什么影响
聊天记录 / 业务状态聊天记录像聊天截图；状态像办事进度单。“用户说过”还要变成系统可遵守、可恢复的事实。
GraphRAG / LangGraph前者帮助查知识关系，后者组织执行流程。可以组合，不能互相替代；都不是必须接入的前提。
Function Calling / 实际执行前者像开出办理申请，后者才是真的去办。拿到真实回执才能说成功，合法JSON不等于参数或权限正确。
建单 / 解决问题建单像取号；接单像开始办理；解决还要有处理结果。分别展示状态，不能把“已转人工”算作已解决。
人时 / 日历时间一个人做8小时是8人时；两个人各做8小时是16人时。依赖与等待无法简单除以人数；产品核验和账号等待单列。

模型与模型接入

用大白话说：我们到底要不要接？

它干什么： 模型负责听懂、看图、把话说清楚，也可以提出工具调用。

什么时候需要： 用户表达很乱、照片需要解释，或当前回答格式不稳定时。

现在怎么接最省事： 先保留现有接口，选一个已开通的云模型，用同一组案例测试。

它解决不了什么： 它不会自动拥有最新说明书，也不会保证工单真的创建成功。

模型负责理解、表达和提出候选动作；事实来自知识，执行权限来自业务服务。模型名称不是客服架构。

最小数据边界： 输入：消息、图片、已确认事实、适用证据；输出：经过校验的观察、缺失信息、候选动作。
