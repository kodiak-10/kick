# AI Coach 产品重构任务说明书

本文件不是问题回顾，而是面向实现的重构执行说明。

目标：把当前版本从“研究型 Demo / 算法界面”重构为“可持续迭代的产品级 AI 运动教练原型”，并为后续 Xcode 原生化迁移建立清晰边界。

---

## 1. 当前版本定位

当前版本可以定义为：

- 技术路线基本成立
- 实时骨架、基础规则、足球场景分析已经跑通
- 但产品完成度不足
- 仍然属于原型验证阶段，而不是成熟软件阶段

因此，接下来的工作重点不是继续堆更多指标，而是完成以下转变：

1. 从“算法展示”转为“训练反馈”
2. 从“骨架可视化”转为“足球动作理解”
3. 从“实时看一下”转为“完整训练闭环”
4. 从“单场景脚本”转为“可扩展运动引擎”
5. 从“Python 原型”转为“Xcode 可迁移产品逻辑”

---

## 2. 重构总原则

所有后续改动必须遵守以下原则。

### 2.1 用户模式优先

用户模式只展示：

- 当前动作
- 当前阶段
- 动作评分
- 关键问题
- 纠正建议
- 训练进度

以下内容默认不得出现在用户模式主界面：

- raw metrics
- 调试字段
- 内部规则名
- 置信度细节
- 多个中间变量
- 开发者状态信息

### 2.2 先产品流程，后算法深挖

在当前阶段，必须优先保证：

1. 用户知道怎么开始
2. 用户知道系统在干什么
3. 用户知道这次训练的结果是什么

而不是优先新增更多低可解释性的指标。

### 2.3 足球专项优先

当前产品的差异化必须明确锚定在“足球专项 AI 教练”。

这意味着：

- 球不是附属物
- 足球专项阶段必须成为主逻辑
- 反馈语言必须以足球训练语境表达

### 2.4 为 Xcode 上架做约束

任何原型层的设计，都要为未来迁移到：

- SwiftUI
- AVFoundation
- Core ML / TFLite / Vision

提供稳定的行为契约，而不是继续把状态和渲染耦合在 OpenCV 主循环里。

---

## 3. 第一优先级：重新定义产品信息层级

### 3.1 首页和实时页必须明确分层

产品至少要有以下页面层级：

1. 启动页 / 首页
2. 运动项目选择页
3. 设备与人物准备页
4. 实时训练页
5. 会话结束页
6. 训练总结页
7. 历史记录页

当前版本至少先实现前 1 到 6 页的产品状态。

### 3.2 实时训练页的信息层级

实时训练页只保留三个核心层：

#### 第一层：主反馈中心

必须固定显示在最显眼区域：

- 当前动作
- 当前阶段
- 当前总评分
- 当前关键问题
- 当前一句话建议

#### 第二层：训练任务层

显示：

- 当前训练目标
- 本组进度
- 已完成次数 / 目标次数
- 当前是否有效识别中

#### 第三层：辅助专业层

显示少量高价值足球与生物力学指标，例如：

- 支撑脚
- 摆动脚
- 触球状态
- 技术分
- 控制分
- 风险分

### 3.3 默认删除或隐藏的字段

以下字段默认移出用户模式：

- 全量角度列表
- 全量原始规则输出
- 所有 debug raw string
- 开发阶段内部标签
- target switch risk
- internal refs
- move ratio
- 所有不直接可读的 proxy 指标

它们只能在开发模式、导出诊断报告或内部日志中出现。

---

## 4. 第二优先级：把足球专项识别从“骨架规则”升级为“动作理解”

### 4.1 需要建立足球专项动作集

当前阶段先收敛到以下足球动作：

1. 传球
2. 射门
3. 停球
4. 变向
5. 启动
6. 急停
7. 跳跃 / 顶球准备

### 4.2 每个动作必须拆成阶段

每个足球动作至少要有阶段定义：

- 准备
- 接近
- 支撑脚落位
- 摆腿
- 触球
- 随挥
- 恢复

当前系统不允许只输出一个模糊动作标签，而缺少阶段解释。

### 4.3 足球专项联合分析必须建立

未来的足球分析应以“人-球联合关系”为中心，而不是“先识别人，再顺便找球”。

必须逐步增加以下指标：

- 触球脚判断
- 支撑脚与球距离
- 摆腿轨迹稳定性
- 触球前躯干控制
- 触球前髋膝踝协同
- 触球后球速/方向变化

### 4.4 技术栈建议

短期：

- 规则 + 时序状态机
- 球跟踪增强
- 事件冻结显示

中期：

- 足球动作规则库
- 足球事件分类器
- 触球关键帧检测器

长期：

- learned event model
- player-ball interaction model
- football technique scoring model

## 5. 第三优先级：把反馈从“参数播报”改成“AI 教练语言”

### 5.1 反馈必须分层

实时反馈至少分为四类：

1. 正向反馈
   - 例如：支撑脚稳定、触球前姿态好、随挥完整
2. 纠正反馈
   - 例如：支撑脚过近、触球瞬间躯干打开不足
3. 风险提醒
   - 例如：膝内扣风险、落地稳定性不足
4. 训练建议
   - 例如：下次训练优先练支撑脚定位与髋部打开

### 5.2 每条反馈必须回答三个问题

每次关键反馈必须尽量回答：

1. 什么问题
2. 为什么会这样
3. 下一步怎么改

示例：

- 问题：支撑脚距离球过近
- 原因：导致摆腿空间不足，击球方向不稳定
- 建议：下一次支撑脚落点后移 5-10cm，并保持脚尖朝目标方向

### 5.3 足球专项语言统一

禁止继续使用过于通用、偏健身或偏算法的表达作为主反馈。

优先使用足球训练语境：

- 支撑脚
- 摆动腿
- 触球点
- 重心转移
- 随挥
- 躯干打开
- 击球稳定性
- 落地控制

---

## 6. 第四优先级：建立完整训练闭环

### 6.1 必须有清晰的产品流程

产品体验必须是：

1. 选择项目
2. 进入准备页
3. 确认人物与设备
4. 开始训练
5. 实时反馈
6. 完成一轮
7. 输出训练总结
8. 保存到历史

### 6.2 会话结束页必须标准化

每次训练结束后，至少输出：

- 本次主要动作
- 本次最突出问题
- 平均评分
- 峰值风险
- 一句话总结
- 下一轮训练建议

### 6.3 训练总结页必须具备

训练总结页至少要有：

- 本次训练总时长
- 有效动作次数
- 动作评分趋势
- 重点问题 Top 3
- 建议优先训练项
- 导出按钮

### 6.4 历史记录必须纳入路线图

即使当前先不完整实现，也必须提前定义数据结构：

- session_id
- date
- sport
- action types
- average scores
- issues
- report path

---

## 7. 第五优先级：建立更像产品的视觉系统

### 7.1 设计方向

产品气质应偏向：

- 专业运动科技
- 简洁
- 有力量感
- 高可信度
- 少而精

而不是：

- 调试台
- 参数控制面板
- 学术原型截图

### 7.2 视觉规范

必须统一：

- 主色
- 警示色
- 成功色
- 字体体系
- 卡片圆角
- 阴影
- 图层透明度
- 骨架绘制风格

### 7.3 主画面优先

视频主体必须永远是视觉中心。

这意味着：

- 文本不能长期压住主体动作
- 左右卡片必须更薄
- 用户模式优先半透明卡片
- 关键事件使用短时悬浮卡，而不是常驻大面板

### 7.4 双语策略

双语不能简单把中英文强行并列在每一行。

建议：

- 用户模式默认中文主导，英文作为辅助小字
- 开发模式可保留双语并列
- 导出报告可使用双语完整版

---

## 8. 第六优先级：建立多运动扩展框架

### 8.1 必须从现在开始拆分“通用引擎”和“专项模块”

建议结构：

- `core`
  - camera
  - tracking
  - pose
  - session state
  - rendering contract
- `sports`
  - football
  - tennis
  - running
  - fitness
- `feedback`
  - coaching language
  - scoring
  - report generation

### 8.2 每个运动专项模块都应有统一接口

统一接口建议：

- `detect_action`
- `detect_phase`
- `score_technique`
- `score_control`
- `score_risk`
- `summarize_feedback`
- `build_report`

### 8.3 当前实现要求

当前优先完成：

- 把足球逻辑从通用实时循环中抽离
- 让后续网球、跑步、健身可以接入同一状态机

---

## 9. 第七优先级：补齐商业化表达

### 9.1 必须重新定义卖点

未来对外表达不应该是：

- 我们能做骨架识别

而应该是：

- 我们能做足球专项动作纠错
- 我们能给出实时 AI 教练反馈
- 我们能输出训练总结和长期成长记录
- 我们能降低专业训练门槛

### 9.2 产品卖点必须围绕结果价值

最终产品卖点建议收敛为：

1. 实时动作纠错
2. 足球专项技术评分
3. 训练后自动总结
4. 个性化成长档案

---

## 10. 工程实施优先级

以下顺序必须严格执行。

### Phase A：先做产品感

1. 重新整理用户模式 UI
2. 删除无关字段
3. 加启动页 / 准备页 / 结束页
4. 固化训练流程状态机

### Phase B：再做足球专项深度

1. 足球动作与阶段状态机
2. 触球时刻识别
3. 支撑脚 / 摆动脚逻辑加强
4. 球-人联合分析增强

### Phase C：再做训练闭环

1. 会话总结
2. 历史记录
3. PDF / 图片报告
4. 趋势图

### Phase D：最后做多运动框架

1. 拆通用引擎
2. 拆专项模块
3. 加运动项目选择
4. 为 Xcode 迁移冻结接口

---

## 11. 当前版本明确要删掉或弱化的内容

以下内容不是“以后再说”，而是要优先弱化：

1. 用户模式中的大段英文原始文本
2. 过多几何指标同时常驻显示
3. 开发模式信息渗透到用户模式
4. 没有训练闭环的单纯实时打分
5. 与足球训练语境无关的反馈表达

---

## 12. 当前版本明确要新增的页面和模块

短期内必须新增：

1. 产品首页 / 项目选择页
2. 标准化准备识别页
3. 会话结束页
4. 训练总结页
5. 历史记录入口
6. 报告导出能力

短期内必须强化：

1. 事件冻结卡片
2. 关键动作高亮
3. 足球专项动作阶段
4. 球-人联动分析

---

## 13. 验收标准

重构后，必须至少满足以下标准：

### 13.1 从视觉上

- 用户模式一眼能看懂
- 主体动作不会被文字压住
- 用户知道第一眼看哪里
- 页面像产品，不像实验界面

### 13.2 从功能上

- 用户知道如何开始
- 用户知道如何结束
- 用户知道这次训练结果是什么
- 系统能给出足球专项反馈，而不是只播报姿态参数

### 13.3 从架构上

- 状态机明确
- 足球逻辑可拆分
- 多运动可扩展
- 能为 Xcode 原生化提供清晰迁移边界

---

## 14. 给 Codex 的直接执行要求

后续实现必须按如下方式推进：

1. 先改 UI 信息层级，不再先加新参数
2. 先做完整训练流程页，再继续深挖分析能力
3. 先做足球动作阶段化，再做更复杂模型
4. 用户模式永远优先于开发模式
5. 任何新增字段都必须回答：用户为什么需要看到它
6. 任何新增算法都必须回答：它是否真正提高足球专项反馈价值
7. 所有新功能都要考虑未来 Xcode 原生化迁移

---

## 15. 一句话结论

当前最重要的任务不是继续证明“系统能识别”，而是把系统重构成一个：

更像产品、真正懂足球、能形成训练闭环、并且可以迁移到 Xcode 上架的 AI 教练平台。
